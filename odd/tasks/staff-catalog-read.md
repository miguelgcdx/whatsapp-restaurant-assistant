Other methods on catalog =>405/Allow GET. Every new catalog success/error has a random server-owned request_id and Cache-Control:no-store; do not change legacy access envelopes.

New success JSON is exactly the selected structure `{data:{items:[{id,name,price:{amount_minor,currency,exponent},available,version}],next_cursor,restaurant:{open,version}},request_id}`. Money/version are nonnegative canonical decimal strings <=MaxInt64, item IDs lowercase UUIDv4, names valid UTF-8/nonblank<=200 code points; nullable next_cursor explicitly null at end. Invalid stored values =>safe500/internal_error, no clipping/coercion. Unconfigured restaurant/cursor capability or database/JWKS failure =>safe503/temporarily_unavailable; missing/invalid bearer401, revoked/inactive membership403. Safe error codes/messages, no SQL/DSN/tokens/key data/provider payload. Go does not substitute an Origin check for JWT authority (BFF owns browser origin policy in a later slice).

GET accepts no body/framing payload and pagination query only: default50, limit1–100, nonempty opaque ASCII cursor<=2048, reject duplicate/unknown fields and malformed encoding. Validation failures400 with no catalog mutation or outbound effects. Authenticate before retrieving protected catalog rows or honoring continuation. Bound each new response to <=512KiB serialized UTF-8 JSON including envelope/request_id; size-check actual bytes before writing success. Because validated names have bounded length and pages<=100, no arbitrary menu/order cap is needed.

Add a NEW catalog store page API without changing existing Menu()/Settings()/Initialize()/SetAvailability() contracts. Query PostgreSQL with stable ascending `(created_at,id)`, scoped restaurant and keyset position, at most limit+1 rows; never load the whole catalog to serve a page. Return current restaurant availability alongside the page. Continuation identifies last EMITTED row, not lookahead; no dropped/duplicate rows on static traversal, no successful nonadvancing empty cursor. Live availability may change between requests; no cross-request DB transactions or snapshot guarantee. No schema or generated SQLC changes needed.
